# Claude Code 프롬프트 묶음 — 노션 보기·속성 위젯 앱

작성 2026-10-30. 짝 문서: `RESEARCH.md`(조사), `CLAUDE.seed.md`(불변 규칙 초안).
현재 앱을 만들 때 쓴 방식을 그대로 쓴다: **PRD 먼저 → Phase마다 plan 모드로 계획 승인 → 테스트 먼저 구현 → 게이트(test lint, 실기기, 스크린샷) → 커밋.**

## 0. 시작하는 법 (Windows PC)

```powershell
# 1) 새 저장소 만들기(가칭 notion-widgets). 현재 앱 폴더와 나란히 둔다.
mkdir ..\notion-widgets ; cd ..\notion-widgets ; git init
# 2) 문서 복사 (경로는 본인 폴더에 맞게)
mkdir docs
copy ..\myNotionCalendar\docs\next-app\RESEARCH.md docs\RESEARCH.md
copy ..\myNotionCalendar\docs\next-app\PROMPTS.md docs\PROMPTS.md
copy ..\myNotionCalendar\docs\next-app\CLAUDE.seed.md CLAUDE.md
# 3) Claude Code를 plan 모드로 시작하고 아래 프롬프트 A를 붙여 넣는다.
claude --permission-mode plan
```

- 현재 앱 저장소(`..\myNotionCalendar`)는 **읽기 전용 참고·복사 원본**이다. 수정하지 않는다. 가져올 모듈 목록은 RESEARCH §6에 있다.
- 참고 앱은 `ccr-6810527c-es92oi` 브랜치(또는 이를 합친 main)를 체크아웃한 상태여야 한다. 이 브랜치에 `docs/PRD.md`·`docs/plans/phase-6.md`(설계 검증 메모 15건)와 이 문서들이 있다.
- 노션 토큰은 앱 화면에서 직접 입력한다(프롬프트·파일에 쓰지 않는다).
- 노션 연결의 기능(콘텐츠 읽기·업데이트·삽입, 사용자 정보 읽기)을 켜고, 테스트할 DB 페이지마다 연결을 추가해 둔다.

## A. 프롬프트 A — PRD 작성 (코드는 쓰지 않는다)

```text
[Prompt A: PRD]
새 안드로이드 앱의 PRD를 쓴다. 지금은 코드를 쓰지 않는다. 먼저 계획을 보여줘.

배경
- 사용자는 노션의 기존 데이터베이스를 쓴다. 이 앱은 노션 "보기"(표·보드·캘린더·타임라인·리스트·갤러리·차트)를 읽어 같은 모양의 앱 화면과 홈 화면 위젯으로 번역하고, 속성(텍스트·숫자·선택·다중 선택·상태·날짜·사람·파일과 미디어·체크박스·URL·이메일·전화번호·수식·관계형·롤업·생성 일시·생성자·최종 편집 일시·최종 편집자·버튼·장소·ID)을 사용자가 취사선택해 보여주고, 가능한 것은 위젯과 앱에서 고칠 수 있게 한다.
- 이미 비슷한 앱이 있다: ../myNotionCalendar (읽기 전용 참고). 그 앱의 docs/PRD.md와 CLAUDE.md의 구조·규칙·검증 방식을 이 PRD의 모범으로 삼아라(요구사항 ID 표, P0/P1/P2, 완료 기준, 근거 표기, Phase 지시문, 테스트 기준, 리스크, 결정 사항).

읽을 것(전부 읽고 시작)
1. docs/RESEARCH.md — 조사 결과. §0 발견 5가지, §2.3 속성 능력표, §3 보기→위젯 매핑, §4 안드로이드 제약, §5 아키텍처, §6 가져올 자산과 함정, §7 확인 필요 항목.
2. ../myNotionCalendar/docs/PRD.md, ../myNotionCalendar/CLAUDE.md, ../myNotionCalendar/DESIGN.md
3. ../myNotionCalendar/docs/plans/phase-6.md 의 '검증 메모'(실제 설계 검증에서 나온 함정 15건)

할 일
- docs/PRD.md를 쓴다. 요구사항 ID 접두사: VW(보기), PR(속성), WD(위젯 템플릿), IN(상호작용), CF(위젯 설정), SY(동기화), ST(저장), PF(성능·안정), SEC(보안), A11Y(접근성). 속성 22종 각각에 PR-NN을 하나씩 준다(읽기·쓰기·위젯 셀·편집기·로컬 정렬/필터/그룹의 완료 기준을 한 줄씩). 보기 7종 각각에 VW(앱 화면)와 WD(위젯) 항목을 따로 준다.
- 우선순위 정의: P0 = 해당 Phase에서 반드시, P1 = 다음, P2 = 이후. 한 번에 다 만들지 못하므로 P0는 "표·리스트·캘린더 + 체크박스·선택·상태·날짜·숫자·텍스트" 같은 얇은 세로 조각이 되게 잡아라(근거를 쓸 것).
- §7의 확인 필요 항목 12개를 PRD §"확인 필요"에 옮기고, 각 항목의 확인 방법과 결과 반영 위치를 적어라. 확인 전에 가정한 내용은 '가정'이라고 표시해라.
- docs/DESIGN.md 초안: ../myNotionCalendar/DESIGN.md의 토큰·선택 색 10종 팔레트를 가져오고, 위젯 밀도(크기별 단계) 규칙을 추가.
- 개발 Phase 계획: docs/PROMPTS.md의 'B. Phase 프롬프트' 초안(Phase 0~10)을 출발점으로 다듬어라. Phase마다 대상 ID, 게이트, 실기기 확인 항목을 적고, 다듬은 최종 Phase 지시문은 PRD §Phase별 지시문에 옮긴다.
- CLAUDE.md는 이미 복사돼 있다. PRD와 어긋나는 규칙이 있으면 고치지 말고 차이를 보고해라.

지켜야 할 것
- 범위: 페이지 본문 편집, 수식 재계산, 노션 DB·보기 생성/수정, 폼·지도·대시보드 보기, 서버·웹훅, iOS는 비목표. 비목표도 PRD에 적는다.
- 노션 공식 문서를 직접 읽을 수 있으면 읽고 RESEARCH와 다른 점을 보고해라. 읽을 수 없으면 읽을 수 없다고 적고 RESEARCH의 △ 항목을 가정으로 유지해라.
- 설계안을 쓴 뒤, 서브에이전트로 적대적 설계 검토를 한 번 돌려라(경쟁 조건·마이그레이션·위젯 제약·누락). 나온 문제와 고친 내용을 PRD 부록 '설계 검증 메모'에 남겨라.
- 결정이 필요한 것은 한 번에 최대 4개씩 AskUserQuestion으로 물어라. 후보: 앱 이름·패키지명, 저장소 위치(새 저장소 vs 현재 앱에 모듈 추가), 첫 세로 조각의 보기·속성 범위, 개인 설치(APK)만 vs 스토어 배포, 지원 최소 기기(S25 우선 가정).
- 끝나면 PRD 요약(요구사항 수, P0 수, 확인 필요 수)과 열린 질문만 보고하고, 승인을 기다려라. 승인 전에는 파일 외 어떤 코드도 만들지 않는다.
```

## B. Phase 프롬프트 (PRD 승인 뒤 한 번에 하나씩)

각 프롬프트 앞에 `docs/PRD.md를 기준으로`를 붙이고, plan 모드에서 계획을 먼저 받는다. 게이트는 항상 `gradlew.bat test lint assembleDebug` 통과 + 실기기 설치 + 스크린샷. 확인 못 한 항목은 '미검증'.

```text
[Phase 0 — 기반]
빈 앱과 빌드 기반을 만든다.

- 모듈 뼈대는 CLAUDE.md의 모듈 규칙대로 만들고, `:widget`이 `:core:notion`에 의존하지 못하게 빌드 설정으로 막는다(위반하는 의존을 일부러 넣어 빌드가 실패하는 것을 확인).
```

```text
[Phase 7 — 위젯 템플릿 1 + 위젯 설정]
대상: WD(표·리스트·보드·캘린더), CF 전체.
- 템플릿: 표(열 N개 계산, 열 페이지 버튼), 리스트, 보드(1~3열, 열 전환 칩), 캘린더(현재 앱 위젯 3종 일반화). 크기별 밀도 단계, 글꼴 배율 곱, 넘치면 한 단계 단순하게.
- 위젯 설정 화면: 데이터 소스 → 보기(또는 직접 구성) → 속성 취사선택·순서·역할 → 상호작용 켜기 → 테마·투명도 → **실시간 미리보기**. 레시피를 `widget_recipes`에 저장하고 위젯마다 따로 둔다.
- 새 위젯 종류를 넣을 때마다 갱신 목록·"배치된 위젯 있음"·자정 알람·미리보기(WG-08)·설정 액티비티 종류 판별을 같이 고친다. 위젯 액션이 위젯 클래스를 하드코딩하지 않게 `AppWidgetManager`로 종류를 찾는 공용 함수를 쓴다.
- Glance 단위 테스트: 크기별 자식 10개 이하, 클릭 액션.
- 게이트: 4종 × 크기 3단계 × 글꼴 최소·최대 스크린샷, 비행기 모드 표시, 위젯 반영 0.5초 이내 로그.
```

```text
[Phase 8 — 위젯 템플릿 2 + 통합 탭 위젯]
대상: WD(타임라인·갤러리·차트), 통합 탭 위젯.
- 타임라인 위젯: 줄 = Row(앞 간격·막대·뒤 간격 비중). 갤러리: `LazyVerticalGrid` 2~3열 + 미리 줄인 썸네일. 차트: number=텍스트, column·bar=비중 막대(최대 8~12, 넘으면 상위 N+기타), line·donut=예산 있는 비트맵.
- 비트맵은 동기화·갱신 작업에서 만들어 디스크에서 읽는다. 위젯 수·크기 버킷 수를 곱해 총량이 `6×폭×높이`를 넘지 않는지 계산하는 함수와 테스트, 최대 크기 위젯 메모리 측정(`adb shell am memory-limiter`).
- 통합 탭 위젯: 탭 줄(보기 3~4개) + 고른 탭 저장(설정 모델·변환에 새 칸을 빠뜨리지 않는다) + 월 이동 같은 액션이 탭 위젯에서도 맞는 위젯을 그린다. 고른 탭의 Flow만 모은다.
- 게이트: 위젯 IllegalArgumentException 0, 3종 스크린샷, 탭 전환 0.5초 이내.
```

```text
대상: IN 전체.
```

## C. 매 세션 꼬리말 (필요하면 프롬프트 끝에 붙인다)

```text
- 계획을 먼저 보여주고 승인 전에는 파일을 고치지 않는다.
```

## D. 열린 결정 (프롬프트 A가 사용자에게 묻는다)

1. 저장소: 새 저장소(권장: 규칙·모듈이 다르고 현재 앱은 안정 운영 중) vs 현재 앱에 모듈 추가.
2. 첫 세로 조각의 범위: 표·리스트·캘린더 × 체크박스·선택·상태·날짜·숫자·텍스트(권장) vs 보기 7종 전부 얕게.
3. 배포: 개인 설치(APK, 현재 앱과 같음, 권장) vs 스토어. 스토어면 공개(OAuth) 연동·서버·개인정보 처리가 필요해 범위가 크게 달라진다.
4. 현재 앱과의 관계: 둘 다 두기(권장) vs 새 앱이 캘린더·해빗·가계부까지 흡수. 흡수한다면 해빗·가계부의 도메인 로직(주 목표·예산·중복)을 "위젯 동작·계산 속성"으로 일반화할 수 있는지 먼저 검토.
